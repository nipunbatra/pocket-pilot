Why did it choose left when the gap was middle?

We reproduced that collision at 1× in Classroom mode. The road moved zero pixels while the model answered. The answer took 267.5 ms: left 50.8%, middle 24.1%, right 25.1%. The response had a valid structure, but selected a blocked lane. This was a prediction failure in the local model path, not a delayed answer.

We then tested four prompt formulations on identical images: the three original scenes plus eighteen new scenes covering every open lane, every car lane, and two barrier heights. Each request asked one lane question. No answer was corrected using the game state.

Does the original model make the same mistake?

Yes, on this frame. We ran Liquid’s original d1-omni-600M checkpoint with its native PyTorch code, official image preprocessing and unquantized float32 weights. It also chose left: 49.7% left, 28.4% middle, 21.9% right. The browser chose left with 50.8%. The browser conversion alone cannot explain this wrong answer.

Why does Snake look better in the tweet?

The Atomic Chat post identifies d1-3B on an RTX 3090. Our browser option is d1-omni-600M on WebGPU. These are different models and execution environments. Liquid’s release post announces both; its technical article describes 600M as experimental and an early research release.

The Snake video illustrates how local response speed enables more moves and apples in the same wall-clock time. That combines decision quality with the number of opportunities to act; it does not establish accuracy on identical game states. The exact Atomic Snake prompt, input representation and safeguards were not established from the public post. Liquid’s separate official Snake playground is labelled Text; we should not assume that is the exact same implementation.

What these numbers include

Local wall-clock time includes preprocessing, WebGPU/WASM operators and copying results back to JavaScript. It excludes weight downloads and model preparation. We warmed each input path once before measuring. The three questions run sequentially and share image features. This is not the same measurement as a cloud API round trip. The sample is too small to establish a general speed or accuracy ranking.

The full image stack downloads about 595 MB of model data; text alone about 406 MB, plus the runtime and tokenizer. A fresh image load in the game took 25.8 seconds on this connection. A separate cached prototype load took about one second. Download speed, GPU, memory pressure and browser all matter. First inference can take longer while GPU shaders compile.

What stays on the device

After loading, game images, structured scenes, questions and answers stay in the tab. Hugging Face serves the weights on first use; the browser caches them when storage is available. There is no inference API fee. The page still needs a static host; this is not an installed offline web app.

Reproducible, with limits

The model is pinned to ONNX revision 4ebc1b97bf1477485371c79d1cf8d5e4e8eebfa0: q8 decision weights, q4 embeddings, fp16 vision. We corrected the generic image processor’s initial square resize to preserve the source aspect ratio. An independent ONNX CPU check reproduced the JSON probabilities to within 0.000004, which helps separate model errors from WebGPU errors. A separate native PyTorch float32 check reproduced the same lane choices on the three saved image scenes, all three JSON scenes, and the exact failing live frame. Probabilities differ, so this is agreement on choices, not exact numerical parity.
