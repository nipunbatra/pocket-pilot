02 / Start with the names

A model answers. An API lets our code ask.

We need to separate the model, the way we call it, and the code that uses its answer.

LM / LLM

Language in, text out

A language model works with text. We can give it a JSON description of the road and ask which lane to take.

{ "blocked": ["middle", "right"] }
VLM

It can read the picture

A vision-language model also accepts images. It has to recognize the blocks before choosing a lane.

Road picture → lane answer

API

The software interface

Our program sends a request and reads a response. The API defines the fields; a model evaluates the input.

Request → model → response

Then our code acts.

The returned answer does not move the car by itself. Our controller validates it and chooses when to apply it.

LM means language model; LLM means large language model. VLM means vision-language model. JSON is text with named fields, not a separate visual modality. API means application programming interface: the agreement between programs about requests and responses. A VLM can return ordinary text or structured JSON. The output format and the model's input capability are separate choices.

What did it choose?

{ "choice": "left", … }

Choose a lane, route an item, or flag something for review. The question stays fixed while the input changes.

Request format: OpenRouter Decisions reference

The API takes state and named questions. In this demo the question types are choice, noul and score, explained shortly. Calling this an API does not mean it is a separate robot or autonomous agent. There is no automatic control loop: our application repeatedly captures state, sends the request, reads the result and applies its policy. A typed answer can still be wrong.

07 / The answer shapes

What will the answer look like?

choice A category

We get one of our labels, a probability for each label, and a separate confidence value.

{ "choice": "left",
  "probabilities": { "left": 0.99, "middle": 0.01, "right": 0 },
  "confidence": 0.99 }

noul A probability

A value of 1 means the model estimates a 100% chance of yes. This is a number, not the boolean true.

{ "noul": 1 }

score An ordered scale

The API averages the level numbers using their probabilities. That is why the answer can fall between levels.

0 × 0.1 + 1 × 0.3 + 2 × 0.6 = 1.5Illustrative distribution. Our recorded frame returned score 0.

Even a value of 1 is the model's estimate. We still check what happened in the game.

The first two snippets are excerpts of the recorded answer. The score arithmetic is deliberately labelled illustrative so students see why the value can be fractional. A score of 1.5 is not a 150% danger probability. Noul has no separate confidence field.

Illustrative answers. In this game, only choice steers; noul and score describe the frame.

Ask students which type they would use for "Which lane?", "Is it blocked?", and "How far down the image?". Choice names an option; left and right are not numbers to average. Its probabilities compare the supplied alternatives, while confidence is a separate model-reported estimate, not a guarantee. Noul 0.8 is a probability, not the boolean true; a hypothetical application threshold of 0.7 would classify it as yes, while 0.9 would not. This game does not threshold noul to steer. Score 1.5 summarizes a distribution over the supplied level indices. It does not say the barrier is physically halfway between two positions, and different distributions can have the same average. Reopen the probability distribution when the distinction matters. All values on this slide are illustrative.

09 / Same input, different jobs

Describe the road, or choose a lane?

Both are useful questions. They ask the model to do different work.

CONVENTIONAL CHAT

The middle and right lanes are blocked. Move left…

Useful when a person needs an explanation.

CHAT + JSON SCHEMA

Generate a small object

“Return only a lane from these three labels.”

{ "lane": "left" }

Useful when we define a custom output shape.

DECISIONS

Evaluate fixed options

“Which lane is open?” Use a choice question.

{ "choice": "left",
  "probabilities": { … } }

Useful for a repeated classification or routing step.

Illustrative excerpts. Our chat baseline requests short JSON, with no explanation, so the timing comparison uses a practical baseline.

Chat structured outputs · Clef's option-scoring design

Conventional chat generates tokens, including JSON tokens when using a schema. Specialized decision models may score the allowed options directly; Cloudflare documents this single-forward-pass approach for Clef. The API shape alone does not prove every provider uses identical internals. A schema constrains syntax and labels, not factual correctness. A model-written confidence number is not automatically a calibrated probability. Even decision probabilities need validation on our own data. Choose chat for explanation or open-ended analysis and a decision interface when the allowed outputs are already known.

10 / Why use this API?

Why use Decisions for this game?

The car needs a lane label. We also want to see how the model rated the alternatives.

What we needPlain text LLM callLLM + structured outputDecisions API
Machine-readable resultWe have to interpret the wordingWe supply a JSON schemaThe API supplies the answer types
One of three lanesWe ask for a lane in the promptWe can restrict it to three labelsWe ask a choice question
UncertaintyThe model may describe uncertaintyWe can ask it to write a numberChoice and score include distributions
Best use hereExplain a driving strategyProduce a custom plan or objectAsk the same small questions each frame

We write less code to interpret the answer, and we get a distribution over the supplied choices.

A normal chat model can return structured JSON too. Let's compare the time each approach takes on this game.

Source: OpenAI Decisions guide. Use Responses for explanations/custom schemas; function calling for tool requests.

The useful distinction is the output contract. Chat with a JSON schema can already return a valid lane label. Our chat baseline asks for a short answer with no explanation, so we do not slow it down with extra prose. The next slides use our measured calls. They compare different models and API paths together; they cannot isolate API overhead or establish better calibration, accuracy or cost.

19 / Beyond the game
What could we try in the lab?
Proposed demos for our work. These need their own labelled examples and evaluation.


FIELD PHOTO TRIAGE
Which images can we use?
Input: a field photo. Choice: usable, blurred, obstructed, review.
Demo: sort a photo stream and open uncertain items for an annotator.
SMOKE / KILN MONITORING
Is a plume visible?
Input: camera frames. Noul: probability that a visible plume is present.
Demo: flag candidate clips. Fog, dust and steam need review; a photo does not measure PM2.5.
SOLAR INSPECTION
What needs a closer look?
Input: panel photos. Choice: apparently clear, soiling, shading, review.
Demo: build an inspection queue. Confirm performance with electrical measurements.
WASTE AUDIT
Which category fits?
Input: item or bin photos. Choice: paper, plastic, metal, mixed, review.
Demo: assist campus audits. Include unfamiliar items rather than forcing a label.


These are proposed applications, not capabilities validated by the driving benchmark. Start with image usability because the labels are visible and easy for students to check. A smoke-presence classifier is an event-triage tool, not an emissions inventory or an exposure model. Visible appearance alone cannot establish pollutant concentration or solar output loss. Keep lighting, viewpoint and camera differences in the held-out set. For site imagery, describe land or equipment rather than identifying individual people.






20 / When an image is unnecessary
Some useful decisions start with data.
Text or JSON lets us test Jev as well as the other models.


AIR-QUALITY SENSOR QA
What should we check?
Send recent readings, missing-data flags and a technician's note.
Choice: check timestamp, compare neighbours, inspect device, review.
Action: queue a check; retain the original measurements.
BUILDING ENERGY
Which event needs review?
Send load summaries, occupancy schedules and equipment status.
Choice: expected operation, possible idle load, review.
Action: show an operator the supporting trace.
RESEARCH ASSISTANT ROUTING
Which tool should answer?
Send a question about a place, pollutant or time period.
Choice: observation lookup, map, validated model output, clarification.
Action: call that tool before explaining the result.


Compare against simple rules.
A missing timestamp needs a rule. Mixed notes and context may benefit from a model. Test both on the same cases.


These are application proposals. For VayuChat-like research assistants, use the decision step to select an existing tool or validated dataset, then let a conventional LLM explain the returned evidence. The decision model should not invent pollution observations or replace a physical simulation. For energy or air-quality quality control, deterministic checks are strong baselines. A model can combine contextual notes but must be evaluated against those baselines. Suggested actions here create review queues, not autonomous equipment changes.
